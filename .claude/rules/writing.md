# 文書のルール

このリポジトリで Claude が書く日本語の文章に適用します。返信も説明も Markdown の文書も対象です。

## 全体の流れ

読む人は専門的な話を前提にしていません。上から順に読めば分かるように組み立てます。

- 最初に、何があったのかをざっくり書きます。
- 次に、どういう過程でそうなったのかを書きます。
- 最後に、実装やコードなどの細かい話を書きます。

前提や結果は、説明に入る前に箇条書きでまとめます。読む人が先に全体像を持てるからです。

いきなり実装の話から始めてはいけません。何の話かが分からないまま細部を読むことになるからです。

## 言葉の選び方

専門的な言葉はなるべく使いません。コードの用語も、その仕組み特有の仕様や事情も同じです。

- 普段の言葉で言い換えられるなら、言い換えます。
- 言い換えられない場合は、まず普通の言葉で説明します。そのあとで一度だけ名前を出します。
- オプション名やコマンドは文章の中に混ぜません。コードブロックに分けて書きます。

例を挙げます。

- 悪い例: `--no-verify` を付けると hook をスキップできます。
- 良い例: 保存前の自動チェックを飛ばすには、次の指定を付けます。

```
git commit --no-verify
```

## 文の書き方

文体はですます調で統一します。体言止めは使いません。

- 一文は 45 文字までにします。
- 一文に入れる句読点は 2 つまでにします。
- 箇条書きの各項目も、ですます調の文で終えます。
- 見出しだけは、名詞で終えて構いません。

長くなりそうなときは、文を分けます。読み手のリズムを崩さないためです。

## 段落と箇条書き

段落は積極的に分けます。話題が変わるところで必ず空行を入れます。

箇条書きも積極的に使います。前提や結果を並べるときは、文章にせず箇条書きにします。

## 表と図

表や図も積極的に使います。文章の流れは守った上で、理解を助けるために添えます。

- 複数のものを同じ観点で比べるときは、表にします。
- 選択肢とそれぞれの利点や欠点を並べるときも、表にします。
- 手順の流れや、部品同士の関係を示すときは、図にします。
- 図は HTML で書きます。

表や図は、それだけで置きません。何を見せているのかを、直前の文で一言添えます。

表の各セルは短く書きます。一文にしたい内容は、表の外の文章に出します。

## 使わない言い回し

Claude らしい言い回しは使いません。次のような表現が該当します。

- 「もちろんです」「素晴らしいですね」のような、冒頭の相づちを書きません。
- 「以下に示します」「〜ですね！」のような、定型のつなぎを書きません。
- 「ぜひ〜してください」「他に気になる点があれば」のような、締めの誘いを書きません。
- 「〜と言えるでしょう」のような、ぼかした断定を書きません。
